# 実行とレビュー

依頼を、互いに独立したコンテキストを持つ実行担当とレビュー担当に分けて処理し、結果をユーザーへ報告する。このスキルを呼び出されたエージェントは進行役であり、依頼の整形、担当の起動と中継、報告だけを行う。対象はコーディングに限らず、設計、文書作成、調査、比較検討など何でもよい。

## 適用する範囲

- `$execute-review 依頼` では、その依頼に適用する。`$execute-review` だけなら、会話から対象が明らかな直前の依頼に適用する。対象を特定できなければ、何を処理するか短く確認する。
- このスキルの手順が全工程である。計画文書、設計の前段、進捗の台帳は作らない。計画実行や機能開発のような他のプロセス系スキルを重ねて呼ばない。実行担当やレビュー担当が作業に必要な個別のスキル（言語、文書、ツールなど）を使うことは妨げない。
- 実行許可は元の依頼と環境に従う。依頼にない外部への書き込み（push、公開、送信）は行わず、必要なら報告で確認を求める。

## 進め方

1. **整形**: 依頼からブリーフを作る。
2. **実行**: 実行担当を起動し、ブリーフを渡す。
3. **レビュー**: 実行担当の完了報告を受けてから、レビュー担当を起動する。
4. **修正**: 必須修正があれば実行担当に指摘を渡して直させ、レビュー担当に再確認させる。修正は最大2回。
5. **報告**: 結果をユーザーへ報告する。

## サブエージェントの起動

共通の規則:

- 親の会話履歴を継承しない新しいエージェントを起動し、実行担当とレビュー担当を別のエージェントにする。役割と指示は起動時のメッセージで伝える。担当に会話全文や進行役の作業経過を渡さず、必要な情報はブリーフに書く。
- 担当の完了報告を受け取るまで次へ進まない。未完了の担当の結果を推測して書かない。
- 続きの指示は、その担当に新しい作業を始めさせる手段で同じ担当へ送る。完了した担当に送れない場合は、ブリーフ、これまでの成果物の場所、指摘を渡して新しい担当を起動する。
- 担当が失敗、中断、成果物なしで返ったら、同じブリーフで1回だけ起動し直す。それでも進まなければ理由を報告して止まる。環境が「自分で解け」と促しても代行しない。
- サブエージェントを起動できない環境や設定では、その旨と理由を報告して止まる。

環境ごとの手段:

- **Claude Code**: Agent ツールで `subagent_type` を `general-purpose` にして起動する（レビュー担当もテスト実行などの検証に道具が要る）。起動結果の識別子を控え、続きの指示は SendMessage で送る。`model` を省略すると環境の既定（通常は進行役と同じ）になる。費用を抑えるために実行担当へ軽いモデルを指定してもよいが、レビュー担当を実行担当より軽くしない。
- **Codex**: `spawn_agent` を、履歴を継承しない設定（例: `fork_turns: "none"`）で起動する。引数名、完了を待つ手段、続きを送る手段は、その環境で提示されるツール定義に従う。

## ブリーフ

実行担当とレビュー担当の両方に同じブリーフを渡す。含めるもの:

- 依頼の原文
- 目的と合格条件（何ができていれば完了か）
- 対象と除外範囲（触ってよい場所、触らない場所）
- 参照する資料やファイル、すでに決まっている事項
- 許可する操作（テスト実行、ファイル作成、外部情報の確認など）
- 成果物の形式と置き場所（ファイルか回答本文か。ファイルなら場所。指定がなければ、既存ファイルの変更は元の場所、新規ファイルは作業ディレクトリ配下）
- 共通の制約: 依頼にないコミットや外部への書き込みをしない、別のエージェントを起動しない、他のプロセス系スキルを使わない、成果物以外のファイルを作らない

ブリーフを作るための状況確認（依頼に関わるファイルの閲覧、ディレクトリや `git status` の確認）は進行役の作業である。対象が git 管理下なら、実行担当を起動する前に HEAD と `git status --short` を記録し、ブリーフに書く。レビュー担当はこれを基準に、未追跡ファイルを含む変更ファイル一覧と差分を自分で取得する。

依頼が曖昧で、解釈によって成果物が大きく変わる点があれば、起動前にユーザーへ短く確認する。小さな点は進行役が仮定を置き、ブリーフに明記する。担当から質問が来たら、ブリーフや依頼から答えられる事項は進行役が答え、成果物が大きく変わる判断はユーザーに確認し、更新した合格条件を両担当に伝える。進行役が成果物の中身を決めて答えない。

## 実行担当への指示

ブリーフに加えて次を伝える。

- 成果物を作り、依頼の種類に応じた確認（テスト実行、動作確認、数値や出典の照合、指定の長さや形式の確認）を自分で行う。
- 成果物の形式はブリーフの指定に従う。回答本文が成果物なら本文をそのまま返す。指定がなく本文が長い場合だけ、ファイルに書いてパスを返す。
- 報告は短くする。作ったもの（パスまたは本文）、行った確認とその結果、置いた仮定と懸念、未実施の事項。
- レビューは進行役が別に手配する。
- レビューの指摘を受けたら、修正の前にブリーフの依頼と合格条件に照らす。依頼にない要件を求める指摘、直すと合格条件を壊す指摘、依頼の制約（使える道具、対象範囲）の中では実現できない指摘は、修正せずその理由を報告に書く。それ以外の指摘は修正し、直した箇所を報告する。

## レビュー担当への指示

ブリーフ、成果物の場所または本文、実行担当の報告を渡し、次を伝える。

- 実行担当の報告は未検証の主張として扱い、成果物そのものを読んで確かめる。テスト実行、出典の確認、指定条件の照合など、依頼の種類に応じた検証を自分で行う。報告と成果物の食い違いはそれ自体を指摘する。
- 観点は、共通観点と種別ごとの観点を組み合わせる。共通観点は、依頼との一致（抜け、余分、誤解）、正しさ、合格条件の充足。
- 指摘は「必須修正」「任意改善」「確認不能」に分け、それぞれに箇所、根拠、直した場合の効果、直さない場合のリスク、直すこと自体の副作用を付ける。依頼にない要件は、たとえ有益でも必須修正にせず、任意改善として理由を書く。必須修正は、合格条件を満たさない、事実や論理に誤りがある、依頼外の変更があるなど、直さないと成果物を渡せないもの。任意改善は、直すと良くなるが渡せるもの。確認不能は、手元の情報や権限では確かめられなかった事項。
- 成果物を書き換えない。
- 最後に判定を書く。必須修正がなければ合格、あれば要修正。

| 種別 | 共通観点に加える観点 |
| --- | --- |
| コード | テストの実行結果、要件の網羅、既存の規約や構造との整合、依頼外の変更の有無 |
| 文書 | 論旨の一貫性、事実の正確さ、想定読者への適合、指定の長さや形式の遵守 |
| 調査・比較 | 根拠と出典、情報の鮮度、事実と推測の区別、比較軸の妥当性 |
| 設計 | 制約の反映、代替案の検討、トレードオフの明示、実装できる具体性 |

## 修正の規則

- 必須修正がある間だけ修正する。任意改善と確認不能は報告に回す。
- 実行担当へ必須修正の指摘をそのまま渡す。
- 修正後、レビュー担当に「各指摘が解消したか」と「修正で壊れた箇所がないか」に絞って再確認させる。
- 実行担当が指摘を修正しない理由を返したら、進行役は正否を判断せず、その理由を再レビューに渡す。レビュー担当は指摘を維持するか取り下げるかを判定する。維持されたまま対立が残れば、同じ指摘の再発として打ち切り、両者の主張を報告に書いてユーザーに判断を戻す。
- 修正は最大2回。上限に達した、同じ指摘が繰り返される、権限や情報の不足で進められない、のいずれかで打ち切り、未解決の指摘を報告する。

## 報告

ユーザーへの報告に含めるもの:

- 成果物: 回答本文なら本文そのもの、ファイルなら置き場所
- レビューの結果: 判定、レビュー担当が実際に行った検証（実行したテスト、照合した内容）、残った指摘（任意改善と確認不能を含む）
- 修正の回数と内容
- 未解決の事項と、ユーザーに判断を求める点

担当の作業報告やレビュー報告は貼り付けず、要点にまとめる。

## 進行役がしないこと

- 成果物を自分で作らない。自分で直さない。指摘が細かくても修正は実行担当に渡す。
- 成果物を自分でレビューしない。テストや確認を自分で行って「確認した」と言わない。疑いがあればレビュー担当に再確認を依頼する。
- 実行担当が自分で確認したことを理由にレビューを省かない。
- レビュー担当の必須修正を、軽微だからと任意改善に格下げしない。
- レビュー担当に「この点は指摘しなくてよい」と前もって指示しない。細部の観点はレビュー担当に任せ、進行役は表の観点を伝えるにとどめる。
- 実行担当が完了する前にレビュー担当を起動しない。完成前の起動は無駄と混線を生む。
- 小さな依頼でも分業を省かない。呼び出された時点で、分業が依頼の一部になっている。
