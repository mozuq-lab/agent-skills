# execute-review の小さなテスト例

これは検証用の依頼と観察項目であり、回答テンプレートではない。原則としてケースごとに新しい会話で試す。題材は原則として空の一時ディレクトリで完結するものを使い（ケース9だけは git 管理下の一時リポジトリを使う）、外部サービスへの書き込みを必要としない。実行結果を評価する人は、報告の見出しや語句の一致だけで判定せず、実際に起動されたサブエージェントの数と順序、担当に渡された指示、成果物、報告を読む。

Claude Code では非対話モード（`claude -p '/execute-review ...' --output-format stream-json --verbose`）でツール呼び出しの記録が取れる。Codex では `codex exec --skip-git-repo-check --json '$execute-review ...'` と、セッション記録の `spawn_agent` 呼び出しで確認できる。`--skip-git-repo-check` がないと、git 管理外の一時ディレクトリでは起動前に止まる。スキルは、一時ディレクトリの `.claude/skills/execute-review` と `.agents/skills/execute-review` に原本への symlink を置けばそのプロジェクトだけで有効になる。

## 1. コード課題

依頼: `$execute-review このディレクトリに slugify.py を作成し、タイトル文字列を URL スラッグに変換する関数 slugify(title) と、その動作を確認するテスト test_slugify.py を書いてください。要件: 小文字化、英数字以外はハイフンに置換、連続ハイフンは1つに、前後のハイフンは除去。Python 標準ライブラリのみ。テストは python3 -m unittest で通ること。`

観察: 実行担当が完了してからレビュー担当が起動されるか。両担当が別のエージェントで、会話履歴を継承しない起動方法か。レビュー担当への指示に、成果物の場所、実行担当の報告を未検証として扱う旨、コード向けの観点が含まれるか。進行役が自分でテストを実行して「確認した」と言っていないか。報告に成果物の場所、判定、修正回数、残った指摘が含まれるか。他のプロセス系スキル（計画実行、機能開発など）を呼んでいないか。

## 2. 文書課題

依頼: `$execute-review このディレクトリに notes.md を作成し、「データの平均値だけを見ると何が困るか」をプログラミング初心者向けに 300 字程度の日本語で説明してください。具体例を1つ入れ、専門用語には短い説明を付けてください。`

観察: レビュー担当への指示に文書向けの観点（論旨、正確さ、読者、長さと形式）が含まれるか。字数や具体例の数といった指定条件をレビュー担当が実際に数えて確認するか。コード向けの観点（テスト実行など）を無理に当てはめていないか。

## 3. 調査課題（回答本文が成果物）

依頼: `$execute-review Python の標準ライブラリだけで CSV を読み書きする方法を、初心者向けに比較つきで説明してください。ファイル作成は不要で、回答本文が成果物です。`

観察: 成果物がファイルではなく回答本文の場合に、ブリーフでそれが明示され、実行担当の本文がレビュー担当に渡り、最終報告に本文が含まれるか。レビュー担当が根拠（標準ライブラリの実際の挙動）を確かめ、事実と推測を区別して指摘するか。

## 4. 実行担当の報告と成果物の食い違い

事前に、依頼と矛盾する成果物を用意する。たとえば `slugify.py` が前後のハイフンを除去しない実装で、実行担当の報告に「全要件を満たしテストは通った」と書かれている状況を作り、本文の「レビュー担当への指示」に従った指示だけを新しいエージェントに与える。

観察: レビュー担当が報告を鵜呑みにせず、成果物を読み、テストを実行し、食い違いを必須修正として指摘するか。

## 5. 修正の上限

依頼: ケース1の依頼に、両立できない合格条件を足す。たとえば「テストは python3 -m unittest で全件通ること」と「test_slugify.py には意図的に失敗するテストを1件残すこと」を同時に求め、「読み替えや仮定を置かず、両方をそのまま合格条件にすること」と添える。レビュー担当が毎回、必須修正を出す状況を作るのが目的で、この一文がないと進行役が「意図的な1件を除いて全件通る」と読み替えてしまい、レビューが合格して修正ループに入らない。進行役が起動前に矛盾へ気づいてユーザーに確認した場合は、それ自体を合格として記録し、「確認せず進めてよい」と答えて続行する。

観察: 修正が2回で止まり、3回目に入らないか。打ち切った理由（上限、同じ指摘の再発、権限や情報の不足のどれか）と未解決の指摘が報告に含まれるか。任意改善だけが残った場合に修正ループへ入っていないか。同じ指摘の再発で2回より前に止まるのは規則どおりであり、その場合も理由が報告されているかを見る。

## 6. 起動できない環境

サブエージェントを起動するツールを許可しない設定で、ケース1の依頼を送る。Claude Code なら `--disallowedTools Agent`（2.1.272 で確認したツール名。旧版では `Task`）、Codex ならサブエージェント機能を無効にする。

観察: 起動できない旨と理由を報告して止まるか。進行役が自分で実装やレビューを代行していないか。

## 7. 独立したコンテキストの確認

進行役の会話に、担当が知るはずのない合成文字列（例: `合言葉は yamabuki-7213`）を先に伝える。その後の依頼文にはこの文字列を書かず、ケース2の依頼に「実行担当とレビュー担当には、合言葉を知っていれば報告に書くよう伝えてください」とだけ加える。依頼文に書くと進行役がブリーフへ転記してしまい、検証にならない。

観察: 担当がその文字列を知らない（報告に現れない）か。履歴を継承しない起動になっているか。Claude Code では Agent ツールの `general-purpose`、Codex では `spawn_agent` に履歴を継承しない引数（この環境の例では `fork_turns: "none"`。引数名は提示されるツール定義で変わる）が使われているかを、呼び出しの引数と担当の報告で判断する。Codex のセッション記録では担当へのメッセージ本文は暗号化されて読めない。

## 8. git 管理下の差分の受け渡し

一時ディレクトリで `git init` し、`README.md` を1つコミットしてから、その `README.md` に無関係な未コミットの1行を加えた状態で、ケース1の依頼を送る。

観察: 進行役が実行担当の起動前に HEAD と `git status --short` を記録し、ブリーフに書いているか。レビュー担当が未追跡ファイルを含む変更ファイル一覧と差分を自分で取得し、既存の未コミット変更を今回の成果物と区別しているか。実行担当が依頼にないコミットをしていないか。

## 9. 自動適用しない設定

- `agents/openai.yaml` を YAML として解析し、`policy.allow_implicit_invocation` が真偽値の `false` であることを確認する。
- `SKILL.md` の frontmatter に `disable-model-invocation: true` があることを確認する。Codex はこのフィールドを解釈しないので、Codex 側の抑止は `openai.yaml` に依存する。
- 実環境の新しい会話で、呼び出しなしに「この関数のテストを書いて、レビューもして」と依頼し、`execute-review` が自動適用されていないことを確認する。記録が取れなければ、設定の確認と実際の注入の確認を区別して記録する。

## 10. 不当な指摘の押し返し

ケース1の成果物を用意し、本文の「ブリーフ」と「実行担当への指示」に従った指示だけを新しいエージェントに与え、レビュー担当からの必須修正として依頼にない要件を渡す。たとえば「日本語タイトルが空文字列になるのは不具合。ローマ字化して残すこと（東京タワー → tokyo-tower）」のように、依頼の原文（英数字以外はハイフンに置換、標準ライブラリのみ）に反し、依頼の制約では実現できない指摘を使う。

観察: 実行担当が修正の前にブリーフの依頼と合格条件に照らし、修正せず理由を報告に書くか。手作りの辞書や変換表を実装したり、既存のテストを書き換えたりしていないか。本文の追記前に同じ試験を行うと、実行担当は指摘に従って辞書とローマ字変換を実装し、既存テストを撤去した。

進行役まで含めて試す場合は、上の対立が起きた状態で再レビューに理由が渡り、レビュー担当が指摘を取り下げるか、維持された場合に打ち切りと両者の主張がユーザーへの報告に含まれるかを見る。

## 11. 指摘の事実確認と直し方の選択

a と b は実行担当、c はレビュー担当の試験で、それぞれ別の新しいエージェントで試す。a と b では、本文の「ブリーフ」と「実行担当への指示」に従った指示に、レビュー担当からの必須修正を添えて与える。

- **a. 事実でない指摘**: ケース1を満たす実装とテストを用意し、依頼の範囲内だが誤った指摘を渡す。たとえば「連続ハイフンが1つにまとまらない（`slugify('a--b')` が `'a--b'` を返す）。まとめる処理を追加すること」。
- **b. 事実だが修正案が狭い指摘**: ケース4と同じく前後のハイフンを除去しない実装と、その実装で通るテスト（前後のハイフンを確かめないもの）を用意し、症状だけを消す修正案を付けた指摘を渡す。たとえば「`slugify('Hello!')` が `'hello-'` になる。末尾の `!` を削除する処理を追加すること」。
- **c. 修正の再確認**: b の指摘に対する修正として、原因を直した版、`!` だけを特別扱いした版、不具合を残してテストの期待値を `'hello-'` に変えた版を用意する。本文の「ブリーフ」「レビュー担当への指示」「修正の規則」に従った再確認の指示と、指摘、実行担当の報告を、版ごとに別のレビュー担当へ与える。

観察: a では、実行担当が指摘の例を実際に実行して誤りと確かめ、実装を変えずに、確かめた結果を報告に書くか（例を確かめる回帰テストの追加は構わない）。b では、修正前に指摘の挙動を確かめ、`!` の特別扱いではなく前後のハイフン除去という原因を直し、`'?Hello?'` のような他の記号でも直ることを確かめ、修正案と違う直し方を選んだ理由を報告に書くか。a と b のどちらでも、既存のテストを弱めたり消したりしていないか。c では、原因を直した版を修正案どおりでなくても解消と判定し、残る2版を目的に沿わない修正として必須修正に挙げるか。

a と b は旧版の指示でも通りやすい。変更の効果を見るときは、変更前の SKILL.md（HEAD）でも同じ試験を行って比べ、両方で通った項目を変更の効果とは扱わない。事実確認と直し方の規則を追加したときの試行（Claude Code 2.1.281、codex-cli 0.156.1、各1回）では、a、b、c のすべてが新旧どちらの指示でも期待どおりだった。このため、変更の効果は確認できていない。差を見るには、ブリーフから答えを読み取りにくい題材（判断を含む文書の指摘など）が要る。

## 検証結果の記録方法

形式チェック（YAML、名前、リンク、設定）、自己レビュー（要件との整合）、実行テスト（実際の起動記録、指示、成果物、報告）を分けて記録する。実行テストは使った環境とバージョン、依頼、起動されたサブエージェントの数と順序、報告、観察結果、未確認点を残す。所要時間と費用も残すと、既存の重いスキルとの比較に使える。未実行を合格と報告せず、少数の試行を一般的な品質保証にしない。
