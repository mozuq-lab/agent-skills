# casebrief-lite

小さな修正（バグ修正、数ファイルの機能追加、仕様の微調整）について、**テスト観点**と**設計の入り口**を 1 画面ぶん出す。ケースを実行できる粒度まで詰めるのは利用者に任せる。このスキルの仕事は「何を確かめるか」と「どこから手を付けるか」を外さないこと。サブエージェントは使わず、1 回の読み取りで出力まで進む。

引数: `$ARGUMENTS`

Claude Code では上の行が `/casebrief-lite` に続く文字列に置き換わる。置き換わらずに `$ARGUMENTS` のまま残っている時（Codex など）は、`$casebrief-lite` に続く文字列を引数とする。何も続かなければ空として扱う。

## 1. 対象を決める
引数を上の行から順に照らし、最初に当てはまった行で読む。

| 引数 | 読むもの |
| --- | --- |
| 空 | `git diff HEAD`（未コミットとステージ済み）と、`git status --porcelain` で `??` の付いた未追跡ファイル（直接読む）。コミットが 1 つも無いリポジトリでは `git diff HEAD` の代わりに `git diff --cached`。どれも空なら、会話の直前で話していた修正。それも無ければ対象を 1 行で尋ねて止まる |
| `#123`・PR の URL | `gh pr view <番号> --comments` と `gh pr diff <番号>`。`#123` が PR でなければ（`gh pr view` が失敗したら）Issue の行へ |
| Issue の URL・`issue 45` | `gh issue view <番号> --comments`。まだコードが無い修正として扱う |
| `..` を含む文字列、または `git rev-parse --verify --quiet <引数>` が通るもの | コミット範囲なら `git diff <範囲>`（範囲は三点の `main...` の形を勧める。二点の `main..` は main 側だけが進んだ分も逆向きに混ざる）。ブランチ名だけなら `git diff <既定ブランチ>...<ブランチ>`。既定ブランチは `git symbolic-ref --short refs/remotes/origin/HEAD` で求め、失敗したら `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` |
| それ以外の文 | 修正の説明。まだコードが無い修正として扱う |

- まだコードが無い修正では、説明に出てくる語（画面名・関数名・エラーメッセージ・設定キー）で grep し、変更が入りそうな場所を見つける。
- PR の head が手元で checkout されていなければ、`git fetch origin pull/<番号>/head` の後に `git grep <語> FETCH_HEAD` と `git show FETCH_HEAD:<path>` で PR 側のコードを読む。作業ツリーは切り替えない。

**完了条件**: 何を・なぜ変える（変えた）かを 1〜2 文で言え、変更点ごとにファイルと関数（またはそれが入る予定の場所）を挙げられる。

## 2. 周辺を読む
変更点ごとに次の 3 つを埋める。見つからなければ「無し」と書く。
- **直接の影響**: 変更した関数・型・設定・画面の振る舞いがどう変わるか。
- **波及先**: 変更したシンボルや設定キーの呼び出し元・参照元（grep で探す）。共有の関数、シリアライズされるデータ、公開 API、既存データの読み込みは特に追う。
- **既存テスト**: 対象を覆うテストの場所と層（unit / integration / e2e）。似たテストがあれば、追加先の候補として控える。

Issue 本文・PR の説明・コメント・docs に仕様の根拠があれば読む。根拠の無い期待は §5 の仮定に回す。

**完了条件**: すべての変更点について 3 項目が埋まっている。

## 3. 観点を選ぶ
`references/viewpoints.md` を読み、変更点ごとに当てはまる観点を選ぶ。
- 修正全体で次の 3 種類を各 1 行以上入れる。**修正の確認**（バグ修正なら、再現手順が直ったこと）、**回帰**（変えていない近傍の振る舞いと §2 の波及先）、**Never**（この修正で起きてはならないこと）。
- 範囲・区分・状態・条件の組合せを持つ入力には、同じファイルの技法メモを当てる。落とし穴の項目は具体例に反映する。
- 観点は 5〜7 個を目安に、10 個までにする。超えたら優先度の低いものを「省いた観点」として 1 行にまとめる。

**完了条件**: すべての変更点に観点が 1 つ以上付き、各観点に具体例が 1 つある。

## 4. casebrief に回すか判定する
次のどれかに当たれば、§5 の出力の末尾で casebrief（1 機能単位で E2E のテスト計画まで作るスキル）に回すことを提案する。
- 新しい画面や機能に当たる、または複数の機能にまたがる。
- 観点が 10 個に収まらない。
- 確認事項が 5 件以上ある、または仕様の根拠がほぼ無い。
- Playwright の E2E テスト計画として残したい。

## 5. 出力する
チャットに次の型で出す。ファイルへの書き出しは頼まれた時だけ行い、場所の指定が無ければ尋ねる。

```markdown
## 変更の要約
- <何を・なぜ（1〜2 文）>
- 影響範囲: <ファイル/関数> → 波及先 <…>
- 既存テスト: <場所と層。無ければ「無し」>

## 設計の入り口
- 推奨: <方針>（理由 1 行）
- 代案: <方針>（採らない理由 1 行）
- 触る場所: `path:line`, …
- 判断が分かれる点: <…>

## テスト観点
| # | 観点 | 具体例（条件 → 期待） | 技法 | 層 | 優先 |
| --- | --- | --- | --- | --- | --- |
| 1 | <…> | <…> | <…> | unit | 高 |

省いた観点: <…>

## 仮定と確認事項
- 仮定: <…>（依存する観点: #2, #5）
- 確認: <…>

casebrief に回す: <§4 で当たった目安>。`_intake/source.md` の下書きを書き出しますか？
```

書き方:
- **具体例**は、前提となる状態やデータを条件側に書き、期待を観測できる形で書く。「正しく動く」ではなく「400 と `invalid email` を返す」、「すぐに表示される」ではなく「送信から 3 秒以内に完了画面が表示される」。1 つの具体例には確認を 1 つだけ入れる。
- **技法**は `references/viewpoints.md` の C 節の名前（境界値分析・同値分割・状態遷移・デシジョンテーブル・組合せ・回帰・エラー推測）から選ぶ。どれも当たらない行は「—」。
- **層**は unit / integration / e2e / 手動。§2 の既存テストと同じ層に置けるならそれを選ぶ。
- **優先**: 高＝落ちたら修正の意味が無い、中＝近傍の回帰、低＝念のため。
- 書くことの無い行（代案、判断が分かれる点、省いた観点、casebrief に回す）は行ごと省く。設計の入り口は方針と場所までにとどめる。
- 仕様に無いことは仮定として書き、その仮定に依存する観点の番号を付ける。仮定が外れた時に見直す範囲がそれで分かる。

**完了条件**: 4 見出しがすべてあり、テスト観点の各行で 6 列が埋まっている。

## 6. source.md の下書きを書き出す
§5 の提案に利用者が応じた時だけ行う。
1. feature 名を利用者に尋ねる。英数字で始まり、英数字・`_`・`-` だけにする（`[A-Za-z0-9][A-Za-z0-9_-]*`）。
2. `test-design/<feature>/_intake/source.md` に次の形で書く。
   - 先頭に `# <機能名> の仕様` と 1〜3 行の概要。
   - 本文は画面や項目ごとの `## §n <見出し>` 節に分け、§5 で決まった振る舞いだけを書く。ファイルや関数など実装の場所は書かない（casebrief の intake は本文を確定した仕様として読む）。
   - 仮定と確認事項は末尾の `## 未確定` 節に、「<確認したいこと>（暫定: <仮定>）」の形で列挙する。
3. `test-design/config.yaml` が無ければ、`casebrief init --feature <feature>` を実行するよう案内する（init は既存の source.md を上書きしない）。
