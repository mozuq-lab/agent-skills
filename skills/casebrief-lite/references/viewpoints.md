# 観点と技法メモ

casebrief の知識ベース（casebrief リポジトリの `src/casebrief/data/kb/` にある `viewpoints.yaml` `techniques.yaml` `defects.yaml` `oracle.yaml`）を小さな修正向けに要約し、KB に無い汎用の観点を足したもの。A は層を問わない観点（★は KB に無い独自の行）、B は画面を持つ修正の観点、C は技法ごとの落とし穴。

## A. 層を問わない観点

| 観点 | 確かめること | よくある不具合 |
| --- | --- | --- |
| 修正の確認 | 報告された再現手順・条件で、期待どおりになるか | 再現条件の一部しか直っていない |
| 回帰 | 変えていない分岐・呼び出し元・他の利用箇所が前と同じか | 共有関数を直して別画面が壊れる |
| Never | 起きてはならないこと（禁則、無効入力の受理、二重実行、残してはいけない値）が起きないか。「必ず〜する」の裏返しではなく、具体的に起きうる事象を書く | エラー後に古い値が残る |
| 入力値 | 空・null・未指定、上限と下限、文字種、形式、全角と半角 | 空文字と null の扱いが分岐でずれる |
| ★エラー処理 | 例外・失敗応答の種類、メッセージ、リトライ、後始末 | 失敗時に途中まで書き込まれる |
| ★状態 | 前の操作や処理の状態が残るか、状態ごとに結果が変わるか | エラー表示が次の操作でも消えない |
| ★条件の組合せ | 複数の条件・フラグ・権限が同時に成り立つ時の優先順位 | 同時に複数違反した時の扱いが未定義 |
| 連続・同時実行 | 連打、二重送信、並行リクエスト、排他 | 押下回数分の処理が走る、売り切れ後も確定できる |
| 日時 | 日またぎ。★月末、うるう年、タイムゾーン、期限ちょうど | 23:59:59 と 0:00:00 で判定が逆転する |
| 権限・アクセス | URL 直アクセス。★権限の無い利用者、他人のデータ | 公開前のページに直アクセスできる |
| ★データ互換 | 既存データ、マイグレーション、設定の既定値、古いクライアント | 新しい必須項目が既存レコードに無い |
| ★外部連携 | 外部 API の失敗・遅延・想定外の応答 | タイムアウト時に成功扱いになる |
| 性能 | ★件数が増えた時、ループ内の問い合わせ、応答時間の目安。時刻・タイマーの精度 | 一覧で件数ぶんクエリが走る、アラームの発火が遅れる |

## B. 画面を持つ修正の観点

| 観点 | 確かめること |
| --- | --- |
| レイアウト | 配置・サイズ・整列、長い値での崩れ |
| 文言 | 誤字、表記（数値・日時）、文字化け、文字切れ |
| ボタン・リンク・画像 | 表示位置と順序、ホバーやクリック時の変化 |
| 入力項目の表示 | 項目名、初期値、選択肢の内容と順序、入力不可表示と実際の入力可否の一致 |
| フォーカス | Tab 移動の有無と順序 |
| 入力の制御 | 文字数（コピー＆ペースト経由を含む）、文字種、形式、チェックボックスの上限、ラジオの排他 |
| エラー表示 | 出るべき時に出るか、出方（画面内・ダイアログ・遷移）が仕様どおりか |
| 画面遷移 | 遷移先、遷移の仕方（同じタブ・新しいタブ） |
| 画面間の引き継ぎ | 前の画面の入力が次の画面に正しく出るか |
| ブラウザバック | 戻る操作で、完了済みの処理をやり直せてしまわないか |

## C. 技法メモ

**境界値分析**（範囲のある数値・長さ・日時）
- 単位（文字かバイトか、時・分・秒、整数か小数か）を先に確定する。全角と半角を 1 文字と数えるか、サロゲートペアや結合文字をどう数えるかも確かめる。
- 「まで」「以上」「未満」「超える」の解釈を先に決め、範囲内の端と範囲外の隣を別の具体例にする。
- UI が入力自体を抑止する境界では、「入力後に保持されている値」を期待にする。
- 日時の境界は秒まで書く。マイナスや圏外のような「あり得ない」範囲も境界として検討する。ただし到達させる操作が無い境界は無理に作らず、対象外とした理由を残す。

**同値分割**（結果が同じになる入力の集まりが複数ある）
- 仕様に書かれない無効区分（空、上限超え、文字種違反、形式違反）を洗い出す。
- 無効区分は 1 つの具体例に 1 つだけ入れる。複数入れると、どの違反で拒否されたか分からない。
- 任意項目の空は有効区分、必須項目の空は無効区分になる。
- 文字種と文字数のように掛け合わせる入力は、有効になるのが一部の組合せだけのことがある。観点ごとに単独で有効・無効を決めない。

**状態遷移**（同じ操作でも状態により結果が変わる）
- 表に無い状態とイベントの組は「何も起きない」か「エラー」かを決め、Never の候補にする。
- 同じ画面でもエラー表示中は別の状態として扱う。
- 元の状態へ戻る操作が仕様にあるかも確かめる。戻り方が仕様に無ければ確認事項にする。無いことを Never にはしない。
- 「遷移しない（自己ループ）」と「そのイベント自体が起こり得ない」を書き分ける。

**デシジョンテーブル**（複数条件の組合せで結果が決まる）
- 条件を真偽に単純化しすぎない。3 値以上なら分ける。
- 同時に複数の違反がある組合せを忘れない。優先順位が仕様に無ければ確認事項にする。
- あり得ない組合せの根拠には「仕様上の禁則」と「条件同士の包含関係による矛盾」の 2 種類がある。片方だけ探すと見落とす。

**組合せ（2 因子間網羅）**（独立な因子が多く全組合せが多すぎる）
- 因子間に依存があるならデシジョンテーブルを使う。
- 全部 ON・全部 OFF のような重要な組合せは手で足す。

★**回帰**（変えていない振る舞いが保たれているか）
- SKILL.md §2 の波及先ごとに、代表的な呼び出し 1 つを具体例にする。既存テストが覆っているならその名前を挙げ、追加は不要と書く。

★**エラー推測**（仕様や技法から出てこない、起きがちな失敗を狙う）
- A 節の「よくある不具合」と、同じ箇所の過去の不具合（Issue・コミット履歴）から具体例を作る。
