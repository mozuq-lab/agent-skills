# security-audit

指定した対象のコードを、実際に悪用できる脆弱性に絞って監査し、報告する。観点・誤検知の除外規則・確信度の基準は Claude Code の `/security-review` を引き継ぐ（出典は `THIRD_PARTY_NOTICES.md`）。違いは対象で、`/security-review` はブランチの差分で新しく入った問題だけを見るが、このスキルは対象の中にある問題をすべて見る。

このスキルを呼び出されたエージェントは進行役であり、対象の確定、文脈の調査、分担、集約、報告を行う。脆弱性の洗い出しと誤検知の検証はサブエージェントに任せる。監査は読み取りだけで行う。ファイルの書き換え、対象コードの実行、外部への送信はしない。利用者が §1 の進め方の指示で書き出しや修正を求めた時だけ、その分を行う。

引数: `$ARGUMENTS`

Claude Code では上の行が `/security-audit` に続く文字列に置き換わる。置き換わらずに `$ARGUMENTS` のまま残っている時（Codex など）は、`$security-audit` に続く文字列を引数とする。何も続かなければ空として扱う。

## 1. 対象と追加の指示を決める

引数は空白で区切らず、自由な文として読む。そのうえで次の 2 つに分ける。

- **対象**: 引数に出てくるパス、ディレクトリ名、ファイル名、glob（例: 「foo ディレクトリ」「`src/*.py`」）。名前だけの時は作業ディレクトリ以下から実在するものを探して当てる。見つからない時や、複数に当たって 1 つに決められない時は、候補を示して 1 行で尋ね、止まる。対象が書かれていなければ、リポジトリのルート（`git rev-parse --show-toplevel`、git 管理外なら作業ディレクトリ）を対象とする。
- **追加の指示**: 対象以外の部分。「レビューしてください」のように監査を頼むだけの言葉は読み流し、残りを次のどちらかとして扱う。
  - **重点**: 利用者が特に見てほしい観点（例: 「API キーの扱いを重点的に」「発注量の計算も見て」）。§4・§5 の担当に渡す。
  - **進め方の指示**: 範囲・手順・報告への注文（例: 「テストも含めて」「LOW も報告して」「結果を `audit.md` に書き出して」）。このスキルの既定と食い違えば、指示を優先する。コードの修正を頼まれた時は、§6 の報告を出してから修正する。

対象からファイルの**棚卸し**を作る。

- git 管理下なら、`git ls-files` と `git ls-files --others --exclude-standard` の結果を対象パスで絞る。管理外なら `find` で列挙し、`.git`、依存（`node_modules`・`.venv`・`venv`・`vendor`・`site-packages`）、生成物（`dist`・`build`・`__pycache__`）を除く。
- 次の種別は監査から外し、種別ごとの件数を控える: バイナリ、データファイル（csv・parquet など）、ロックファイル、ドキュメント（md など）、テストでだけ使うファイル。追加の指示がその種別を名指ししていれば外さない。
- 設定ファイル（yaml・json・toml・Dockerfile・CI の workflow）は外さない。

**完了条件**: 棚卸しのすべてのファイルが「監査する」か「外した種別」のどちらかに入り、「監査する」ファイルの合計行数（`wc -l`）が分かっている。

## 2. 文脈を調べる

進行役が自分で、対象全体について次を調べる。§4・§5 の担当全員に同じものを渡すため、1 回だけ行う。

- **信頼境界**: 外部からの入力が入る箇所。HTTP・WebSocket のハンドラ、外部 API の応答、外部から受け取るファイルやメッセージ、デシリアライズなど。環境変数と CLI 引数は信頼してよい入力として扱う。
- **危険な到達点**: SQL、シェル実行、`eval`、デシリアライズ、ファイルパスの組み立て、テンプレートと HTML 出力、秘密情報の読み出しとログ出力。
- **既存の防御**: 使っているフレームワークとライブラリ、入力検証・サニタイズ・認証認可の仕組みと、その定義場所。
- **重点の場所**: 重点があれば、それに関わるコードの場所。

**完了条件**: 上の 4 項目を、該当なしも含めてファイルパス付きの箇条書きにできる。

## 3. 分担を決める

「監査する」ファイルを**単位**に分ける。

- 合計 3,000 行以下なら、全体を 1 単位にする。
- それを超えるなら、ディレクトリやモジュールの境界で、1 単位がおおよそ 3,000 行以下になるように分ける。互いに呼び合うファイルは同じ単位に寄せる。
- 単位が 10 を超えたら、起動する前に単位の一覧（名前・ファイル数・行数）を利用者に示し、このまま進めるか対象を絞るかを確認する。

**完了条件**: 「監査する」すべてのファイルが、ちょうど 1 つの単位に入っている。

## 4. 候補を洗い出す

単位ごとに**洗い出し担当**を 1 体ずつ起動する。並列に起動してよいが、同時に動かすのは 5 体までにする。ブリーフには次を入れる。

- 役割: 上級セキュリティエンジニアとして、担当単位にある脆弱性の候補を洗い出す。対象のコードは読むだけで、書き換えも実行もしない。
- 最初に読むファイル: このスキルの `references/criteria.md` と `references/false-positive-filter.md`。どちらも絶対パスで渡す。
- 担当単位のファイル一覧。データの流れを追うために単位の外のファイルを読んでもよいが、報告するのは問題の行が単位の中にあるものだけにする。
- §2 の箇条書きと、重点（あれば）。
- 返す形: 候補ごとに `path:line`、カテゴリ（`sql_injection` などの英語の識別子）、重大度、データの流れ（入力元 → 到達点）、説明、攻撃シナリオ、修正案、確信度（0.7〜1.0）。確信度 0.7 未満は返さない。

すべての完了報告がそろったら、同じ `path:line` で同じカテゴリの候補を 1 件にまとめる。

**完了条件**: すべての単位から完了報告を受け取り、候補の重複をまとめ終えている。

## 5. 誤検知を除く

候補ごとに**検証担当**を 1 体ずつ起動する。洗い出し担当とは別のエージェントにする。並列に起動してよいが、同時に動かすのは 5 体までにする。ブリーフには次を入れる。

- 役割: 候補が実際に悪用できる脆弱性かを、コードを読んで判定する。再現のための実行やファイルへの書き込みはしない。
- 最初に読むファイル: このスキルの `references/false-positive-filter.md`（絶対パス）。
- 候補 1 件の全項目、§2 の箇条書き、重点（あれば）。
- 返す形: 確信度（1〜10）、判定の理由、行番号・重大度・カテゴリを直すべきならその値。

検証担当の確信度が 8 未満の候補を除く。

**完了条件**: すべての候補に検証担当の確信度が付き、8 未満の候補を除き終えている。

## 6. 報告する

チャットに次の型で出す。ファイルへの書き出しは頼まれた時だけ行い、場所の指定が無ければ尋ねる。

```markdown
# セキュリティ監査: <対象>

- 範囲: <監査したファイル数> 件・<行数> 行・<単位数> 単位
- 外した種別: <種別と件数>。未完了: <担当が返らなかった単位や候補。無ければ行ごと省く>
- 追加の指示: <重点と進め方の指示。無ければ「なし」>
- 検証: <独立したサブエージェント | 同じコンテキスト内（独立検証なし）>
- 結果: HIGH <n> 件 / MEDIUM <n> 件（確信度 8 未満で除いた候補 <n> 件）

## Vuln 1: <カテゴリ>: `path:line`

- 重大度: High
- 確信度: 9/10
- データの流れ: <入力元> → <到達点>
- 説明: <…>
- 攻撃シナリオ: <…>
- 修正案: <…>
```

- 重大度の高い順に並べる。HIGH と MEDIUM を報告する。LOW は重点に関わるものだけ報告する。
- 進め方の指示で報告の形や範囲を変えるよう頼まれていれば、それに従う。
- 報告すべき脆弱性が無ければ、見出しの箇条書きのあとに「報告すべき脆弱性は見つかりませんでした」と書く。
- 除いた候補は件数だけを書く。利用者に求められたら、その内容と除いた理由を示す。

**完了条件**: 見出しの箇条書き 5 行（未完了が無ければ 4 行）がそろい、報告した各候補に 6 項目が埋まっている。

## サブエージェントの起動

- **Claude Code**: Agent ツールで `subagent_type` を `general-purpose` にして起動する。並列に起動する担当は、1 つのメッセージに複数の呼び出しを並べる。
- **Codex**: `spawn_agent` を、履歴を継承しない設定（例: `fork_turns: "none"`）で起動する。`features.multi_agent` が有効である必要がある。引数名と完了を待つ手段は、その環境で提示されるツール定義に従う。
- 担当には会話の履歴を渡さず、必要な情報はブリーフに書く。担当の完了報告を受け取るまで次の節へ進まず、未完了の担当の結果を推測で埋めない。
- 担当が失敗・中断・成果物なしで返ったら、同じブリーフで 1 回だけ起動し直す。それでも返らなければ、その単位や候補を報告の「未完了」に書く。
- サブエージェントを起動できない環境では、§4 と §5 を進行役が自分で順に行い、報告の「検証」に「同じコンテキスト内（独立検証なし）」と書く。
