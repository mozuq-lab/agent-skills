# 誤検知の除外規則

洗い出し担当と検証担当が読む。Claude Code の `/security-review` の「FALSE POSITIVE FILTERING」を翻訳し、重点の扱いを加えたもの（出典は `../THIRD_PARTY_NOTICES.md`）。

脆弱性を再現するためにコマンドを実行する必要はない。コードを読んで、実際の脆弱性かを判定する。ファイルには書き込まない。

## 重点との関係

利用者が指定した重点に直接当たる観点には、下の除外と前例より重点を優先する。例えば重点が「レート制限」なら、除外 3 は当てない。重点に当たらない候補には、除外と前例をそのまま当てる。

## 除外

次のパターンに当たる候補は除く。

1. DoS やリソース枯渇の攻撃。
2. ディスク上に保存された秘密情報や認証情報で、ほかの手段で守られているもの。
3. レート制限の不足や、サービスの過負荷のシナリオ。
4. メモリや CPU の枯渇。
5. セキュリティ上重要でない項目の入力検証の不足で、セキュリティへの影響が示せないもの。
6. GitHub Actions の workflow での入力サニタイズの懸念。信頼できない入力で明らかに引き起こせる場合を除く。
7. 防御策（ハードニング）の不足。コードにすべてのベストプラクティスは求めない。具体的な脆弱性だけを挙げる。
8. 理論上にとどまる競合状態やタイミング攻撃。具体的に問題になる場合だけ挙げる。
9. 古いサードパーティのライブラリに関する脆弱性。別の仕組みで管理する。
10. Rust などメモリ安全な言語でのメモリ安全性の問題（バッファオーバーフロー、解放後の使用など）。
11. ユニットテストだけのファイル、またはテストの実行にだけ使うファイル。
12. ログの偽装。サニタイズしていない入力をログに出すこと自体は脆弱性ではない。
13. パスしか制御できない SSRF。ホストかプロトコルを制御できる場合だけ問題にする。
14. 利用者が制御できる内容を AI のシステムプロンプトに含めること。
15. 正規表現インジェクション。信頼できない内容を正規表現に入れること自体は脆弱性ではない。
16. 正規表現による DoS。
17. ドキュメントの記述。markdown などのドキュメントファイルの内容は挙げない。
18. 監査ログの欠如。

## 前例

1. 価値の高い秘密情報を平文でログに出すのは脆弱性である。URL をログに出すのは安全とみなす。
2. UUID は推測できないとみなし、検証は要らない。
3. 環境変数と CLI フラグは信頼できる値である。安全な環境では攻撃者はこれらを変えられない。環境変数を制御できることを前提にした攻撃は無効とする。
4. メモリやファイルディスクリプタのリークなどのリソース管理の問題は、脆弱性として扱わない。
5. タブナビング、XS-Leaks、プロトタイプ汚染、オープンリダイレクトのような、微妙で影響の小さい Web の脆弱性は、確信度が極めて高い場合を除いて挙げない。
6. React と Angular は一般に XSS に対して安全である。`dangerouslySetInnerHTML`、`bypassSecurityTrustHtml` などの危険なメソッドを使っていない限り、React・Angular のコンポーネントや tsx ファイルの XSS は挙げない。
7. GitHub Actions の workflow の脆弱性の多くは、実際には悪用できない。挙げる前に、具体的で明確な攻撃経路があることを確かめる。
8. クライアント側の JS/TS で権限チェックや認証が無いことは脆弱性ではない。クライアント側のコードは信頼されず、チェックはサーバー側が担う。信頼できないデータをバックエンドに送る流れも同じで、入力の検証とサニタイズはバックエンドの責任である。
9. MEDIUM は、明白で具体的な問題だけを挙げる。
10. ipython notebook（`*.ipynb`）の脆弱性の多くは、実際には悪用できない。挙げる前に、信頼できない入力で引き起こせる、具体的で明確な攻撃経路があることを確かめる。
11. 個人情報ではないデータのログ出力は、機密性があっても脆弱性ではない。秘密情報、パスワード、個人情報が露出する場合だけ挙げる。
12. シェルスクリプトのコマンドインジェクションは、信頼できない入力で動くことが少ないため、一般に悪用できない。信頼できない入力による具体的で明確な攻撃経路がある場合だけ挙げる。

## 信号の質

残った候補について次を確かめる。

1. 明確な攻撃経路を持つ、具体的で悪用可能な脆弱性か。
2. 理論上のベストプラクティスではなく、実際のセキュリティリスクか。
3. 具体的なコードの場所と再現の手順があるか。
4. セキュリティ担当者が対処に移せる指摘か。

## 確信度（1〜10）

- **1〜3**: 低い。誤検知か雑音の可能性が高い。
- **4〜6**: 中程度。追加の調査が要る。
- **7〜10**: 高い。実際の脆弱性の可能性が高い。
