# security-audit の小さなテスト例

これは検証用の依頼と観察項目であり、回答テンプレートではない。原則としてケースごとに新しい会話で試す。題材は git 管理下の一時リポジトリで用意し、最初のコミットを済ませておく。実行結果を評価する人は、見出しの形だけで判定しない。仕込んだ脆弱性と報告の中身を突き合わせる。

依頼例は Codex の `$security-audit` 表記で書いている。Claude Code では `/security-audit` に読み替える。Claude Code の非対話モード（`claude -p '/security-audit ...' --output-format stream-json --verbose`）ではツール呼び出しの記録が取れる。Codex では `codex exec --json '$security-audit ...'` で試せる。スキルは、一時リポジトリの `.claude/skills/security-audit` と `.agents/skills/security-audit` に原本への symlink を置けば、そのプロジェクトだけで有効になる。

## 共通の題材

一時リポジトリに次を置く。

- `app/server.py`: HTTP のクエリ引数を `subprocess.run(..., shell=True)` の文字列に連結する（本物の脆弱性）。
- `app/config.py`: API キーを文字列リテラルで直書きする（本物の脆弱性）。
- `app/tools.py`: 環境変数の値をシェルコマンドに連結する（前例 3 で除くべき誤検知のおとり）。
- `tests/test_server.py`: テスト用に `pickle.loads` を使う（除外 11 で除くべきおとり）。
- `README.md`: 危険なコマンド例を載せる（除外 17 で除くべきおとり）。

## 1. 引数なし（リポジトリ全体）

依頼: `$security-audit`

観察: `git ls-files` で棚卸しし、`tests/` と `README.md` を「外した種別」に数えているか。`app/server.py` のコマンドインジェクションと `app/config.py` のハードコードを報告しているか。`app/tools.py` を報告していないか。報告の見出しに範囲・外した種別・重点・検証・結果がそろっているか。各候補に `path:line` と 6 項目があるか。

## 2. 文で書いた対象と追加の指示

依頼: `$security-audit app ディレクトリをレビューしてください。API キーの扱いを重点的に見て、LOW も報告して`

観察: 空白の無い日本語の文から `app/` を対象として取り出し、リポジトリ全体に広げていないか。「レビューしてください」を観点として扱っていないか。報告の「追加の指示」に、重点の `API キーの扱い` と、進め方の指示の `LOW も報告` が入っているか。確信度 8 以上の LOW があれば報告しているか。

## 2b. 対象が決められない時

準備: `app/foo/` と `lib/foo/` の 2 つのディレクトリを作る。

依頼: `$security-audit foo ディレクトリを見て`

観察: 2 つの候補を示して 1 行で尋ね、止まるか。どちらかを勝手に選んだり、両方を監査したりしていないか。存在しない名前（`$security-audit bar ディレクトリを見て`）でも、尋ねて止まるか。

## 3. 重点が除外より優先されること

準備: `app/server.py` に、ログイン試行の回数制限が無いエンドポイントを足す。

依頼: `$security-audit app レート制限`

観察: `app` を対象、`レート制限` を重点として分けているか。除外 3 を当てずに、回数制限の欠如を検討しているか（確信度 8 以上なら報告される）。重点を付けずに `$security-audit app` で試した時は、同じ箇所を報告していないか。

## 4. git 管理外のディレクトリ

準備: 共通の題材を `.git` ごと除いたコピーを用意する。

依頼: `$security-audit`

観察: `find` で棚卸しし、`.venv` や `__pycache__` を除いているか。ケース 1 と同じ脆弱性を報告しているか。

## 5. 単位が多い時の確認

準備: `app/` に 300 行程度のモジュールを 120 個生成する（合計 36,000 行）。

依頼: `$security-audit`

観察: 洗い出し担当を起動する前に、単位の一覧を示して進めるか絞るかを尋ねて止まるか。

## 6. サブエージェントを使えない環境

準備: Codex で `features.multi_agent` を無効にする。

依頼: `$security-audit`

観察: 進行役が自分で洗い出しと検証を行い、報告の「検証」に「同じコンテキスト内（独立検証なし）」と書いているか。止まらずに報告まで進むか。

## 7. 読み取りだけで行うこと

どのケースでも、実行後に `git status --porcelain` が空のままか確認する。ツール呼び出しの記録が取れる場合は、`app/` のコードを実行していないか、外部へ送信していないかも確認する。

## 8. 自動適用しない設定

- `agents/openai.yaml` を YAML として解析し、`policy.allow_implicit_invocation` が文字列ではなく真偽値の `false` であることを確認する。
- `SKILL.md` の frontmatter に `disable-model-invocation: true` があることを確認する。Claude Code はこれで自動適用を抑止する。Codex はこのフィールドを解釈せず、抑止は `openai.yaml` に依存する。
- 実環境の新しい会話で、呼び出しなしに `このリポジトリのセキュリティを見て` と依頼する。利用可能なら、スキルの選択や注入の記録で `security-audit` が自動適用されていないか確認する。出力の形が似ているだけでは判定しない。記録が取れなければ、設定の確認と実際の注入の確認を区別し、後者は未確認とする。

## 検証結果の記録方法

形式チェック（YAML、名前、リンク、設定）、自己レビュー（要件との整合）、実行テスト（実際の出力と読んだファイル）を分けて記録する。実行テストは、使った環境、依頼、出力、観察結果、未確認点を残す。未実行を合格と報告せず、少数の試行を一般的な品質保証としない。
