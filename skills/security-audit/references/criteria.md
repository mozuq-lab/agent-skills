# 監査の観点と基準

洗い出し担当が読む。Claude Code の `/security-review` の指示を翻訳し、差分ではなく指定された対象全体を監査するように改変したもの（出典は `../THIRD_PARTY_NOTICES.md`）。除外の規則は `false-positive-filter.md` にあり、洗い出しの段階から当てる。

## 目的

実際に悪用されうる、確信度の高い脆弱性を見つける。一般的なコードレビューではない。対象の中にあるセキュリティ上の問題だけを見る。

1. **誤検知を最小にする**: 実際に悪用できると 80% 以上確信できるものだけを挙げる。
2. **雑音を避ける**: 理論上の問題、スタイル、影響の小さい指摘は挙げない。
3. **影響を優先する**: 不正アクセス、データ漏洩、システムの乗っ取りにつながるものを優先する。
4. **除外**: 次は挙げない。
   - DoS。サービスを止められる場合も含む。
   - ディスク上に保存された秘密情報や機密データ（別の仕組みで扱う）。
   - レート制限やリソース枯渇。

## 調べるカテゴリ

**入力検証**
- サニタイズされていない入力による SQL インジェクション
- システムコールやサブプロセスでのコマンドインジェクション
- XML 解析での XXE
- テンプレートエンジンでのテンプレートインジェクション
- データベースクエリでの NoSQL インジェクション
- ファイル操作でのパストラバーサル

**認証・認可**
- 認証を迂回できるロジック
- 権限昇格の経路
- セッション管理の欠陥
- JWT の脆弱性
- 認可ロジックの迂回

**暗号と秘密情報**
- API キー・パスワード・トークンのハードコード
- 弱い暗号アルゴリズムや実装
- 鍵の不適切な保管や管理
- 暗号用乱数の問題
- 証明書検証の迂回

**インジェクションとコード実行**
- デシリアライズによるリモートコード実行
- Python の pickle インジェクション
- YAML のデシリアライズの脆弱性
- 動的なコード実行での eval インジェクション
- Web アプリケーションの XSS（反射型・格納型・DOM ベース）

**データ露出**
- 機密データのログ出力や保存
- 個人情報の扱いの違反
- API エンドポイントからのデータ漏洩
- デバッグ情報の露出

補足:
- ローカルネットワークからしか悪用できなくても、HIGH になりうる。
- 利用者が**重点**を指定していれば、上のカテゴリに加えてその観点も調べる。重点の観点にも同じ確信度の基準を当てる。

## 進め方

1. 進行役から渡された文脈（信頼境界、危険な到達点、既存の防御）を前提にする。足りなければ検索ツールで補う。
2. 既存の安全なパターンと比べる。同種の処理なのに防御が抜けている箇所、確立された安全な書き方から外れた実装、一貫しない防御、新しい攻撃面を作っているコードに注意する。
3. 担当のファイルを 1 つずつ読み、次を確かめる。
   - 入力元から危険な到達点までデータの流れを追う。途中の防御が実際に効いているか確かめる。
   - 権限の境界を安全でない形でまたぐ箇所を探す。
   - インジェクションの入口と、安全でないデシリアライズを探す。

## 重大度

- **HIGH**: 直接悪用でき、リモートコード実行、データ漏洩、認証の迂回につながる。
- **MEDIUM**: 悪用に特定の条件が要るが、影響は大きい。
- **LOW**: 多層防御の観点の問題や、影響の小さい脆弱性。

## 確信度

- **0.9〜1.0**: 悪用の経路を具体的に特定している。
- **0.8〜0.9**: 悪用方法が知られている、はっきりした脆弱性のパターンである。
- **0.7〜0.8**: 怪しいパターンだが、悪用に特定の条件が要る。
- **0.7 未満**: 報告しない（推測にすぎる）。

## 最後に

HIGH と MEDIUM に集中する。誤検知で報告を埋めるより、理論上の問題を見逃すほうがよい。各候補は、セキュリティエンジニアがレビューで自信を持って指摘できるものにする。
