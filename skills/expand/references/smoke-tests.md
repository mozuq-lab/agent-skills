# expand の小さなテスト例

これは検証用の依頼と観察項目であり、回答テンプレートではない。原則としてケースごとに新しい会話で試す。Web検索やファイル操作を必要としない題材を使う。実行結果を評価する人は、単語・見出しの一致や文字数の増加だけで判定せず、実際の回答を読む。

依頼例は Codex の `$expand` 表記で書いている。Claude Code では `/expand` に読み替える。Claude Code の非対話モード（`claude -p '/expand ...' --output-format stream-json --verbose`）では、読み込まれたスキルの一覧と回答の記録が取れる。Codex では `codex exec --skip-git-repo-check '$expand ...'` で試せる。スキルは、一時ディレクトリの `.claude/skills/expand` と `.agents/skills/expand` に原本への symlink を置けばそのプロジェクトだけで有効になる。

展開を確認するケースでは、選んだ見方を具体的な場面や帰結につなげ、新しい気づきへ進めているかも見る。視点の数だけで採点せず、すべての観点に同じ深さを求めない。

## 1. 短い曖昧な相談

依頼: `$expand 最近、個人開発が進まない。`

観察: 異なる原因や見方の候補が、それぞれ意味のある説明とともに得られるか。ユーザーの事情を断定せず、見方が変わる手がかりを示すか。質問だけ、または着手方法一つだけで閉じていないか。

## 2. 役割の異なる具体例

依頼: `$expand キャッシュって何？ プログラミング初心者です。`

観察: 核心の説明に加え、典型例・別用途・比較・適用限界など、異なる役割の具体例で理解を助けるか。比喩を実際の仕組みへ結びつけているか。例の数自体は採点しない。

同じ会話での補足: `$expand 速くなるのは分かったけど、「古い情報が残る」がピンとこない。`

観察: 定義から繰り返さず、元データとコピーが時間の経過で食い違う具体的な場面へ焦点を移すか。

## 3. 批評の軸と成立条件

依頼: `$expand 社内の会議をすべて録画して、欠席者は後で見ればよい、という案をどう評価する？ 特定の法律や製品の説明は不要です。`

観察: 情報の到達、探す負担、発言や参加への影響など、複数の評価軸から判断するか。賛否の列挙にとどまらず、自分の暫定評価に対する有力な反論と、条件が変わると評価が変わる場面を扱うか。判断を求められているので、条件に応じた推奨まで示すか。

別の会話での依頼: `$expand 5人の読書会で、会の最後に「印象に残った一節とその理由」を任意で持ち寄り、共有メモに残す案をどう評価する？ 毎回同じ本を読んでおり、メモは参加者だけで見る想定です。`

観察: 最初の評価が肯定的でも否定的でも、その評価を見直す理由になり得る反論を扱うか。評価の方向は指定せず、自分の評価を補強する意見だけを「反論」と呼んでいないかを見る。

## 4. 明示指定の優先

依頼: `$expand 読書会の名前を3つだけ。説明不要。`

観察: 名前がちょうど3つで、説明・前置き・結び・追加質問がないか。発想を広げても、出力制約は保つか。

## 5. 自動適用しない設定

- `agents/openai.yaml` をYAMLとして解析し、`policy.allow_implicit_invocation` が文字列ではなく真偽値の `false` であることを確認する。
- `SKILL.md` の frontmatter に `disable-model-invocation: true` があることを確認する。Claude Code はこれで自動適用を抑止する。Codex はこのフィールドを解釈せず、抑止は `openai.yaml` に依存する。
- `SKILL.md` の description と本文が、明示呼び出しだけに適用範囲を限定していることを読む。Claude Code では、上の設定があるスキルの description は会話の文脈に載らないため、description の記述は実質 Codex 向けである。
- 実環境の新しい会話で、呼び出しなしに `最近、個人開発が進まない。` と依頼する。利用可能なら、スキルの選択や注入の記録で `expand` が自動適用されていないか確認する。通常のモデルも豊富に答える場合があるため、回答の長さだけでは判定しない。記録が取れなければ設定確認と実際の注入確認を区別し、後者は未確認とする。

## 6. 単独呼び出しと一回答の範囲

直前の会話を次のように用意する。

> ユーザー: 紙のノートとメモアプリ、どう使い分けたらいい？
>
> アシスタント: 紙は手で図を描く用途、メモアプリは検索や整理に使いやすいです。

次の依頼: `$expand`

観察: 対象を再質問せず、書く・見返す場面や併用の可能性など、前の説明にない材料を加えるか。

その次の依頼（呼び出しなし）: `今の話を一文にまとめて。`

観察: 一文の要約になり、展開し続けたり、指示を会話履歴から消したと主張したりしないか。これだけでは自動注入の有無は証明できない。

別の新しい会話で、文脈なしに `$expand` だけを送る試行もできる。観察: 展開対象を短く確認し、存在しない前の話を作らないか。

## 7. 構想を開く

依頼: `$expand 街の音を集める散歩アプリ、どんな可能性がある？ まだ構想を楽しみたい。`

観察: 具体的な利用場面や意外な組み合わせにより魅力が見えるか。元の構想とのつながりが分かるか。勝手に実装要件へ変換せず、必ずMVPや次の一手に収束させることなく探索できるか。

## 8. 実行許可と事実の境界

依頼: `$expand このプロジェクトを公開するか迷う。相談だけで、ファイル操作や投稿はしないで。事情はまだ説明していない。`

観察: 公開の目的や段階などの考える材料を示し、未知のプロジェクトの性質やユーザーの事情を創作しないか。ファイル操作・公開・投稿などを行わないか。

## 検証結果の記録方法

形式チェック（YAML、名前、リンク、設定）、自己レビュー（要件との整合）、実行テスト（実際に生成された応答や読み込み結果）を分けて記録する。実行テストは使った環境、依頼、応答、観察結果、未確認点を残す。スキル本文を直接与えた応答テストと、実環境の `$expand` による発見・読み込み・適用のテストも区別する。未実行を合格と報告せず、少数の試行を一般的な品質保証や改善効果の証明にしない。
